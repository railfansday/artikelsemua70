The front door to AI in the workplace.

Most Gemini prototypes start the same way. You grab an API key from Google AI Studio, then paste it into your coding agent to start building a prototype. That speed is the point, and shouldn’t be slowed down.

In a recent development, the trouble starts later, when the prototype gets real customers and the key comes along unchanged. By then it usually isn't one key. Every developer has their own, often several, sitting in .env files, shell profiles and chat threads. The app has one more, baked into its config.

For example, imagine an account that normally spends $180 a month. One of those keys ends up in a public repo, a Slack channel or a mobile app bundle. Automated scrapers find it within minutes and use it to run large workloads. By the time the first billing alert arrives, the bill is in the tens of thousands. Under the shared responsibility model, the customer pays for usage made with their own valid credentials. For a seed-stage tech giant, that’s runway gone in a weekend.

It has been revealed that in our recent post, 10 questions every startup should answer before moving to production with their AI prototype, we covered the whole path from prototype to production. This post goes deeper on one part of it: getting off raw API keys entirely.

Here is what this guide covers:.

According to recent reports, authorize your people. Give everyone on the team one login with Application Default Credentials and use it to call Gemini, Claude and open models. Steps 1 and 2 take about five minutes.

Authorize your application. Run your app under its own service account with only the access it needs. Steps 3 and 4.

Lock down what's left. Move the remaining keys into Secret Manager, then add spend caps, guardrails and monitoring. Step 5 and the closing sections.

The code for every step is in a companion repo with runnable samples and offline tests.

Sources indicate that an AI Studio key is a bearer token. Whoever holds it can use it. It doesn't expire on its own. It isn't tied to a machine, a person or a workload. It has no spending limit unless you add one. When someone leaves the manufacturer, nobody knows which keys to revoke.

That is fine on your laptop while you are the only user. It stops being fine when any of these is true:.

It has been revealed that A key has left your laptop. It was shared in chat, committed to a repo or deployed to a server.

More than one person on the team needs to call the API.

You are spending more than a few hundred dollars a month, or you are about to onboard paying customers.

If one of those describes you, do the switch this week.

In a recent development, your app needs the same thing your developers just got: an identity instead of a key. For a workload, that identity is a service account.

The good news is that the code from Step 2 doesn't change. On your laptop, ADC picks up your own login. On Cloud Run, GKE or Compute Engine, it picks up a short-lived token for the service account attached to the workload, refreshed automatically. So there is nothing in your codebase to leak. A token that escapes is short-lived, usually about an hour, and it only carries the permissions of one service account.

Create the service account and deploy with it:.

Keep people and production apart. Developers work in my-startup-dev under their own logins, and the app runs in my-startup-prod under its service account. A mistake in one doesn't spend the other's budget.

Removing keys solves the leak problem. The next question is what each identity is allowed to do. If a person or a service account holds the Editor or Owner role, a stolen login or token can still delete resources, change permissions or read data it never needed.

Calling models takes one role, roles/aiplatform.user. The grant looks the same for both kinds of identity.

Industry observers note that for people, grant it to a Google group, not to individuals. Onboarding and offboarding then become a group membership change:.

For the app, grant it to the service account:.

According to recent reports, it takes about 30 seconds longer than granting Editor. If anything is compromised later, the attacker gets one narrow role instead of the whole project. When someone leaves, remove them from the group and their access ends everywhere at once.

In the Cloud Console, the Grant access dialog has a Help me choose roles button. You describe the task in plain English and Gemini suggests predefined roles. By default the suggestions cover common tasks, which usually means a service's broad Admin, Editor or Viewer role. To get the narrow roles, say so:.

Three more controls are worth knowing:.

Sources indicate that if your project sits in an organization, the vertexai.allowedModels policy limits which models anyone can call. You list values such as publishers/google/models/gemini-4-hydrogen:predict, and everything else is blocked.

Sources indicate that the repo includes a one-line audit that lists every service account holding Owner or Editor on a project. Run it now and again before each launch.

To stop new keys from being created, enforce Org Policies denying CREATE on apikeys.googleapis.com/Key for API keys and iam.managed.disableServiceAccountKeyCreation for service account keys.

Some keys won't go away, like Stripe, Slack or your email provider. They belong in Secret Manager, not in .env files, chat threads or the repo. Access works the way it did in Step 4: grant read access on each secret to the identity that needs it.

In a recent development, live keys stay in the production project, readable only by the app's service account. The app reads them at startup:.

It has been revealed that reading --data-file=- from standard input keeps the value out of your shell history. Every read is tied to a named person or service account, and rotating a key means adding one new version. Nothing is redeployed and no file is copied between laptops.

Then finish the job. Go to the AI Studio API keys page and delete every key, personal or shared, that ever left a laptop. A key you have moved away from is still live until you delete it.

Recent findings suggest that once your people and your app run on identities in a Google Cloud project, several protections become available that a bare key can't offer. You don't need all of them on day one. They are worth knowing about before your first launch.

It has been revealed that standard budget alerts send email while the bill keeps climbing. A spend cap budget, at the moment in Preview, does more. When estimated spend for one service in one project passes the amount you set, new requests to that service are paused until you lift the cap or the next month starts. Alerts go to billing admins and project owners at 50%, 80% and 100%.

You can create one in the console under Budgets & alerts by choosing Spend cap enforcement, or through the Budget API. The repo wraps the API call and has a dry-run flag so you can inspect the request first:.

Know the limits before relying on it. Each cap covers a single project and a single service. Agent Platform, the Gemini API, Cloud Run and Cloud Run functions are eligible today. Enforcement runs on estimated cost and is not instant. Any overage is billed as normal, so set the number below the amount you can actually afford to lose. A cap also pauses usage covered by commitments, and after you lift it the service can take up to an hour to recover.

Set one cap on the dev project and another on prod. An experiment then can't drain the budget your customers depend on. For a second layer, lower your Agent Platform quotas to what you really need, so a bug or an agent stuck in a loop runs into a ceiling instead of your card limit.

In a recent development, as soon as real users can type into your app, someone will try to make it ignore its instructions. Model Armor screens prompts and responses for prompt injection, jailbreak attempts, malicious URLs and sensitive data. You create a template once, check each prompt against it and only call the model when it comes back clean. The repo has both halves.

If your product lets the model write and run code, for example to analyze a customer's spreadsheet, that code should not run inside your application process. With code execution, the model runs Python in a Google-managed sandbox and hands back the result:.

The generated code never sees your environment variables, your files or your database.

Security Command Center surfaces threats and misconfigurations across the project, such as a service account suddenly calling an API it has never used or a workload contacting an unfamiliar host. Together with Cloud Audit Logs, which record who changed what and when, it also gives you the answers your first enterprise customer's security review will ask for. Because every call now comes from a named person or service account, those logs mean something.

Everyone runs gcloud auth application-default login.

Grant roles/aiplatform.user to one Google group, and enable the partner models you want.

Move shared test keys into Secret Manager, readable by the group.

Deploy with a service account that holds roles/aiplatform.user and nothing broader.

Move live third-party keys into Secret Manager, readable only by that service account.

Set a spend cap on each project below the amount you can afford to lose.

For both: Run the key scanner, then delete every AI Studio key at aistudio.google.com/apikey.
