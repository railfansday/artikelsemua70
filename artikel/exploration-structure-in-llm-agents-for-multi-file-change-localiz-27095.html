Exploration Structure in LLM Agents for Multi-File Change Localization

🌐 Source: Arxiv • 📅 23 Nov 2026 • ⏱️ 1 min read (256 words, 📖 Standard)

arXiv:2606.11976v2 Announce Type: replace-cross Abstract: Fixing an issue starts with finding the files to change, and most benchmark concerns touch several. LLM agents for this task increasingly add structure, such as specialized tools, multiple agents, or code summaries. We ask which of this structure matters when the model is small. We build a coordinator agent with repository tools that limit their output and a reusable registry of subsystem-scoped domain agents. We compare six configurations, each adding structure to the previous one. They are the model alone, a single agent with a Python REPL, a coordinator with only the REPL, the previous structure plus repository tools, then plus the registry map, and finally plus consultation of the domain agents. We also run four published localizers with the same model, two larger-model references, and five non-LLM rankers on 105 multi-file issues from three Python repositories, in audited single-commit checkouts. Most of the gain comes from letting the model explore the repository over many turns. Pooled source-file F1 rises from 0.199 for the model alone to 0.677 for the REPL-only coordinator. The repository tools add a small, non-significant gain, and the registry does not help, lowering pooled F1 by 0.031. A small model in a plain multi-turn agent loop (0.695) thus exceeds all four published localizers (best 0.586), while Codex with a larger model reaches 0.751. For a small model, the agent loop matters more than added agents. New files and narrative documentation remain largely missed. We release the benchmark, predictions, tool logs, and scripts.
