Built for trust and control: Powering the next wave of AI agents across Google Workspace and Google Cloud

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

President, Google Cloud Platform & SRE.

Sources indicate that for over 20 years, we have protected 4 billion users and 13 million organizations in Workspace, and critical enterprise and government systems on Google Cloud. From personal and financial records to board materials, regulated workloads, applications, and AI models, those safeguards protect what matters most. Blocking >99.9% of spam, phishing, and malware, alongside encryption and data residency, follows one principle: your data is yours, and you should always know and decide who can access it.

In a recent development, that trust has powered one of the world’s largest developer ecosystems. Workspace APIs now handle more than 2.8 trillion calls a month, and public Google Drive API traffic alone is more than two-and-a-half times the volume of 2022. More than 18 billion reads from Drive each day come from API callers. Traditional REST APIs were built for human-paced apps where a valid OAuth token implied user intent. As AI agents shift from reading information to acting autonomously at machine speed across email, documents, datasets, and cloud infrastructure, a valid token is no longer enough. Policy checks, data boundaries, and human confirmation have to live in the request path.

Industry observers note that today, Workspace MCP servers and the Workspace CLI are generally available alongside Google Cloud Agent Gateway and unified protections across Workspace and Google Cloud. Builders get modern, agent-ready interfaces, and organizations get the visibility and control to adopt AI agents with confidence.

To help developers build reliable agents faster without forcing security teams to compromise, we are bringing agent-native interfaces to Workspace and Google Cloud:.

Workspace MCP servers: Now generally available, dedicated remote servers for Gmail, Google Drive, Docs, Sheets, Slides, Calendar, Chat, and Tasks. Builders get one standard interface with built-in permission and DLP checks, and native human-in-the-loop (HITL) confirmations for sensitive actions. They also reject non-agent OAuth clients and work with Model Armor, Google Cloud’s prompt-injection screening service.

Workspace CLI: Now generally available for local agents, terminal workflows, and automation, providing structured JSON outputs and scoped OAuth sign-in across Workspace services.

Google Cloud Agent Gateway: A protocol-native gateway for LLM, MCP, and Agent2Agent (A2A) traffic on Google Cloud. It verifies Agent Identities against Agent Registry, enforces IAM policies and default-deny outbound rules, and screens requests with Model Armor.

Together, these interfaces give AI agents open, protocol-native paths built on standards like MCP and A2A. Permissions, confirmations, prompt screening, and audit logging happen automatically, while traditional apps continue to run on existing REST APIs.

Those interfaces sit on a unified security model across Workspace and Google Cloud, with core controls shipping today:.

According to recent reports, policy checks on every request: Under our new Workspace AI Tools Addendum, AI agents must use Workspace MCP servers or the Workspace CLI rather than existing REST APIs. Technical enforcement begins on February 1, 2027, giving builders time to transition. Every call is checked against your organization’s Workspace permissions, DLP rules, and classification labels. On Google Cloud, Agent Gateway enforces IAM and default-deny outbound rules at the protocol layer and routes custom checks through Service Extensions to Identity-Aware Proxy, your own policy engine, or third-party security tools.

According to recent reports, separate agent identities and limits: Admins and people need to tell an AI agent apart from a traditional app or a person, and cap what it can do. Agents connecting to Workspace must use dedicated OAuth client IDs, paired with least-privilege scopes, time-limited approvals (coming soon), and usage quotas (billing begins on April 1, 2027). On Google Cloud, agents receive their own Agent Identity in Agent Registry with no shared or long-lived keys, bounded by IAM policies and organization, folder, and project quotas. Those identities can also carry user-delegated authorization into Workspace when accessing mail or files.

Industry observers note that people stay in charge of high-impact actions: Routine work like creating drafts or summarizing documents runs autonomously, while critical changes require a person to sign off. In Workspace, MCP servers and the CLI enforce explicit user confirmation before agents send email, change Drive sharing permissions, or make bulk edits. On Google Cloud, policy can require multi-factor authentication or human approval before reading sensitive Cloud Storage buckets, changing IAM permissions, or modifying production infrastructure.

Clear visibility and revocation: A one-time consent screen is not enough when agents run continuously. Workspace administrators can view, audit, and revoke AI agents in the admin console, and users will soon be able to view agent activity and revoke access to their emails and files. On Google Cloud, Security Command Center, Agent Observability, Cloud Audit Logs, and Wiz surface unusual behavior. Revoking a Cloud Agent Identity or OAuth grant stops access immediately.

Boundaries for your most sensitive data: Coming soon in Workspace, AI access restrictions extend Workspace DLP and client-side encryption protections to agents. This will allow admins and customers to block agents from accessing messages in Gmail and specific files and folders in Drive. On Google Cloud, VPC Service Controls, Principal Access Boundaries, and Context-Aware Access keep sensitive data inside designated perimeters and verified devices.

Strict rules on your data afterward: Our fresh Workspace AI Tools Addendum sets clear boundaries for AI tools using Workspace APIs. It does not allow permanent raw storage, model training, extended retention of derived data, or API scraping. Derived and user data are removed within a defined window and when a user disconnects. On Google Cloud, Sensitive Data Protection masks sensitive fields before data leaves, and customer-managed or external encryption keys let you cut off access to Cloud agent memory stores immediately.

Workspace developers: Start building with the Workspace MCP and CLI configuration guide, implement user confirmations via MCP and prompt-injection protection such as Model Armor, and review the Workspace AI Tools Addendum.

Workspace administrators: Review connected apps and agents, configure DLP policies for your users, and monitor OAuth activity logs in the admin console.

Google Cloud customers: Register Agent Identities in Agent Registry, place Agent Gateway and Model Armor in front of agents and MCP servers, configure MFA or human approval for sensitive actions, and review IAM, VPC Service Controls, and quota limits.

According to recent reports, with Workspace MCP servers and the Workspace CLI generally available alongside Google Cloud’s agent protections, developers have an open, modern platform to build on. Organizations get the visibility and control to scale AI agents with confidence.
