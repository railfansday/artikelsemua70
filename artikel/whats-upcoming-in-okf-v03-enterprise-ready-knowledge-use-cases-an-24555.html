What’s upcoming in OKF v0.3: enterprise-ready knowledge, use cases, and skills

In June we introduced the Open Knowledge Format (OKF), an open specification that provides plain markdown and YAML to give agents the context they need. In July, v0.2 added trust signals: provenance, trust, freshness, lifecycle, and attestation.

According to recent reports, in production, bundles move between organizations, multiple agents edit the same corpus, and independent tools need to read a bundle the same way. Released today, OKF v0.3 adds precise conformance rules, trust tiers that keep pace with agent edits, self-describing bundles with licensing, safe ways to retire and move knowledge, a stable extension model, and a clear versioning policy. However, the core idea behind OKF stays the same: type is still the only required field, and your existing bundles keep working.

We're also launching OKF use cases, which are community guides for using OKF alongside other industry standards, and two agent skills that let coding agents write and read OKF bundles. Finally, to make cross-organization collaboration easier, we’re moving OKF out of the Google Cloud Platform GitHub org into a standalone organization at https://github.com/open-knowledge-format/open-knowledge-format/.

Let’s take a closer look at what’s new in OKF v0.3.

Sources indicate that v0.3 adds a formal conformance section, allowing independent producers and consumers to work together by design. The spec is self-contained and uses RFC 2119 keywords. It gives one clear answer to the questions that come up when tools from different teams and vendors read the same bundle. The full detail is in the spec, but a few themes matter for anyone building on OKF:.

Built on standard file formats. OKF uses a small, widely supported set of standards: YAML 1.2 frontmatter, CommonMark with GFM tables and footnotes, and RFC 3339 timestamps. If your tools handle those, they handle OKF.

OKF bundles share space with other markdown files. A .md file without a type is skipped by OKF consumers, so README.md, AGENTS.md, CONTRIBUTING.md, and SKILL.md can live inside a bundle without breaking it. Files that aren't markdown, like images or attester code, are assets that concepts can link to.

Consumers handle real-world input predictably. Bundles written by many agents can contain nulls, empty strings, single values where a list was expected, and newly introduced vocabulary. v0.3 specifies how a consumer reads each of these. Consumers accept these inputs without failing, while validators log warnings for malformed entries. A bundle never fails because an optional field is missing or a link is broken.

v0.2 gave every concept a trust tier: unverified, machine-confirmed, or human-reviewed. As agents take on more of the editing, v0.3 makes sure the tier always reflects the latest version of the content. Here's a typical sequence:.

A person reviews a metric definition and signs off.

A week later, an agent refines the definition.

The trust tier now reflects that the person hasn't yet reviewed the latest text.

In v0.3, only current verifications count. A verification is current when it happened at or after the last meaningful change to the content, recorded in generated.at:.

This concept is now machine-confirmed, not human-reviewed, until a person confirms it again. The older sign-off stays in the file as history, and a UI can show it as "reviewed before the last change.".

v0.3 also standardizes actor identifiers. Actors are / for tools, or : for everything else, and v0.3 adds team: next to human: and process:. Only human: earns human-reviewed, because a team name doesn't say which person actually checked the content.

When an agent has access to dozens of bundles, bundle-level metadata supports progressive disclosure so it can pick the right bundle without reading every file. In v0.3, the bundle-root index.md can carry frontmatter about the bundle itself:.

description is written for routing. In one sentence it claims what the bundle covers and when to use it.

license makes clear what you're allowed to do with knowledge you receive from someone else.

okf_version tells a consumer which rules to apply, including compatibility fallbacks for older bundles.

Tools that regenerate index.md must keep this frontmatter.

In a recent development, knowledge evolves, and an agent that finds a deprecated concept should be able to get to its replacement. v0.3 adds superseded_by:.

Consumers that filter to current knowledge follow the pointer and return the replacement. The same mechanism handles moves and renames. Leave a short deprecated concept at the old path that points to the new one, and existing links and stored references keep working.

Links in the body and path fields in frontmatter (resource, superseded_by, executor.resource, and others) now resolve the same way:.

A value with a scheme (https:) is an absolute URL.

A value that starts with / resolves from the bundle root.

Anything else resolves from the directory of the file that contains it, just like on GitHub or in any markdown editor.

For bundles marked v0.2 or earlier, or with no version, a consumer can also resolve paths from the bundle root, so existing bundles keep working.

According to recent reports, v0.3 also makes explicit that links are not parent/child relationships. Only the directory tree defines hierarchy. A link is an untyped, directed relationship, and the text around it says what kind ("joins with," "replaces," "depends on"). Path fields that point at concepts are edges in the bundle graph too.

The community has been extending OKF since v0.1, with typed edges, routing hints, and erasure profiles. v0.3 makes a few extension mechanisms a first-class rule:.

Extension keys are allowed at any level, including inside sources entries, verified events, executor, and attester.

A producer that edits a file must keep the keys it doesn't understand so one tool doesn't overwrite metadata added by another.

Future OKF versions will never define keys that start with x-. Name your keys x--, for example x-acme-owner, and they won't collide with a future spec version.

Recent findings suggest that v0.3 defines OKF's versioning rules. Before 1.0, minor versions may include breaking changes as long as each is documented with a consumer fallback where possible. Starting at 1.0, minor versions will be strictly additive, and released normative text will not change in place.

Sources indicate that the spec also lists what was considered and deferred: typed relationships, the full attestation runtime protocol (receipt and verdict wire formats), semantic-layer attestation, validity windows, and a refuted verification event. Until the community agrees on a form for these, extension keys are the place to experiment. We'd like your proposals.

OKF keeps its core specification small and links to existing domain schemas like Avro, Protobuf, or OpenAPI instead of duplicating them. In practice, though, when your organization already has an established artifact in another standard, such as a schema, a contract, or a spec, what should the OKF concept next to it say, and how should an agent use the two together?

Industry observers note that use cases are layered on the core spec, not part of it. A bundle that ignores them is still a conformant OKF bundle. When a convention proves itself across several use cases, it can be proposed for the core spec through the usual process.

Recent findings suggest that use cases are managed directly in GitHub. Each use case gets its own folder under usecases/ in the OKF repository, for example usecases//. The guide is a .md file in that folder, and any sample bundles or artifacts sit next to it. Use cases are reviewed, versioned, and discussed like any other change.

It has been revealed that if you pair OKF with a standard, please send us a proposal. A rough first draft is welcome. Open a pull request that adds a folder under usecases/ with a .md file in it, and we'll refine it together in review.

v0.3 has two breaking changes, and existing v0.2 bundles stay readable:.

According to recent reports, path fields resolve relative to their file. Fallback: for bundles marked v0.2 or earlier, or with no version, consumers can resolve from the bundle root.

It has been revealed that only current verifications count toward the trust tier. No fallback needed, since tiers can only go down.

Everything else is a clarification or an optional addition. v0.1 fallbacks (timestamp, body # Citations) still apply.

The two skills live in the latest repository and follow the open Agent Skills format, so any agent that supports skills can load them.

okf-generate writes, updates, migrates, and validates bundles from available sources. It cites a source for each claim, records a human review only when that person confirms it, and copies attested computations from a sanctioned source instead of writing them.

Recent findings suggest that okf-consume answers questions from a bundle. For each concept used, it reports the trust tier, status, freshness, and attestation result, and runs attested computations only through the bundle's configured executor and attester.
