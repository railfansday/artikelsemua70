Control Room: A central system to track and stop model workloads across our research infrastructure

🌐 Source: Openai • 📅 09 Nov 2026 • ⏱️ 6 min read (1279 words, 📚 Deep Dive)

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

As our models get more powerful and the associated safety and security risks become bigger, it becomes more and more critical that we can detect potential issues, and promptly stop models in their tracks when needed. To solve this, we built Control Room.

Control Room is a central system to track model workloads across our research infrastructure and stop them promptly when safety or security concerns arise. It connects every research inference workload, including agentic sampling for model training and evaluation, data processing, and more. This works together with our misalignment monitoring systems, and halts model output within 35 seconds of a decision to intervene to stop or pause a job. It has been built to keep working even when other systems fail, and to stop model output if Control Room itself goes down.

Control Room is already deployed across our research infrastructure, where the need is greatest. Our external model-serving stack is already much more centralized by nature, with a well-developed operational capability to promptly take down model deployments if needed.

Control Room works by integrating a few systems: the workload, the inference engine, and the centralized Control Room service.

Recent findings suggest that the workload is the job being run, such as a reinforcement learning experiment, an evaluation, a high-volume sampling or data processing job. We require every research workload that does agentic inference to be associated with an approved safety case.

The inference engine, or just engine, is the model itself. You can think of the engine as the brain of the model, running directly on GPUs. A workload normally uses one or more models, which might be running on one or more different inference engines. The same inference engine might be used by more than one different workload.

The Control Room service tracks jobs and controls whether they are allowed to continue generating model output. Engines check with the Control Room service before fulfilling a request. If a job has been stopped, the service denies the request, preventing further output.

Control Room is integrated in the following way:.

When starting a upcoming job, the workload code requests a new job_id from Control Room.

It has been revealed that whenever the workload needs to sample tokens from a model, it makes a request to an inference engine running that model, passing the job_id. The engine requests permission from Control Room to fulfill that request, passing the job_id along to Control Room.

In a recent development, control Room checks whether that job has been terminated, and if so, it denies the inference request. The engine responds to the workload's inference request with a refusal, stopping further model output from being produced for that job.

The process starts with a researcher launching a job—for example, an experiment or an evaluation.

Job code (or workload code) is owned and run by researchers. Inference engines might be started as part of this job, or standalone engines which are not associated with any particular job might already be running.

According to recent reports, the workload code requests a job ID, associating the job with an approved safety case. The job itself makes this request.

Control Room records the job and returns its identifier. The workload will attach this same ID to its inference requests.

According to recent reports, the request includes the job_id. This request is made directly from the workload code and does not pass through Control Room.

Before fulfilling the request, the inference engine asks Control Room whether this job is still authorized to run.

The job is still authorized, so Control Room grants permission. The inference engine can now fulfill the request.

The model generates a response and the engine sends it back to the research job. The job can use that output and continue its work.

A person or monitoring system tells Control Room to stop this job. Control Room marks its ID as stopped. The workload code remains running.

We do not rely on the workload code to correctly perform a check of whether or not the job is still running.

The engine asks Control Room for permission to fulfill the new inference request, passing along the same job ID.

It has been revealed that when the engine checks permission again, Control Room denies the stopped job. The engine must refuse the inference request.

The engine returns a refusal instead of model output. The research process may remain alive, and the engine remains available to other authorized jobs.

In a recent development, all of our frontier reinforcement learning jobs run with a monitor. A monitor is another model which inspects everything that the model-being-trained is doing, and raises an alert if it detects a problem. For example, our recent DNS-related incident⁠(opens in a new window) was caught by a monitor.

Control Room and our monitoring system are integrated in the following way:.

If the monitoring system detects a potential issue, depending on the details and severity, the monitoring system may decide to stop the job.

In this case, the monitoring system sends a message to Control Room to stop the job, passing the job_id. Control Room records that the job is terminated.

Next time the job having that job_id makes an inference request to sample more tokens from any model running on any engine, the request will be denied, stopping further model output.

The maximum time between the moment when Control Room receives an instruction to stop a job, and the moment when further progress is no longer possible, is 35 seconds. The 35-second lag comes from a caching layer for inference authorization, to support the required volume of traffic. We are working to drive this number down to zero so that we can end jobs instantly.

Recent findings suggest that workloads, including experiments, evaluation jobs, etc., are normally owned and operated by researchers or teams of researchers. As a result, workload code changes often, and is not an ideal place to implement critical load-bearing safety protections. Because of this, our implementation is designed to be resilient to buggy or broken workload code.

According to recent reports, we achieve this by implementing the termination mechanism in the inference layer. Workload code is highly-varied and decentralized. In contrast, there are only a very small number of inference code paths in use across all of OpenAI research, and their deployments are much more centralized and uniform. This means that the inference layer can serve as a bottleneck, where we can get strong guarantees that all model inference running in research is subject to Control Room authorization checks on every inference request. We additionally run continual agentic and programmatic sweeps to check that consumers are not accidentally or maliciously launching rogue engine implementations with Control Room unimplemented or disabled.

It has been revealed that finally, our system “fails closed”, meaning that the Control Room integration in the engines is configured in such a way that if the Control Room service goes down, either due to a system error or because it is disabled for any other reason, including tampering by a bad actor, then all inference requests will be denied until Control Room resumes normal operation. Fail-closed is rolled out now to all frontier model research workloads, and will finish rolling out across all remaining research workloads over the next few days.

In a recent development, control Room is just one part of our holistic approach to safe frontier model training and deployment. We’ll continue to strengthen and expand the system over the coming months, alongside our investments in monitoring for misaligned behavior and security breaches.
